# Decisions taken on the author's behalf — foundation plan

The foundation plan ran as fourteen subagent-implemented tasks, each followed
by a fresh reviewer. Where a reviewer's finding conflicted with the plan's
text, where a brief was ambiguous, or where an implementer raised a doubt,
the controlling session decided and recorded it rather than stopping.

This file is that record, extracted from the run's ledger. Each entry says
what was decided, why, and what it costs if the decision was wrong — so any
of them can be reversed by someone who disagrees.

None of this was approved in advance. Read it as a list of things to
overrule.

- work in this checkout on the existing feature branch rather than a fresh worktree — the fourteen tasks are strictly sequential (Tasks 3–5 consume Task 2's exports, Tasks 8–13 chain through foreign keys), so separate worktrees would fragment the chain, and one extra worktree needs its own `bun install` and its own Postgres volume for no isolation gain over a dedicated branch. Cost if wrong: Marcos cannot use this checkout for anything else while the plan runs; reversible by stashing.
- `superpowers:subagent-driven-development` drives the task loop, and rafa (v0.50.0, on PATH) is used for effort collection at the end and for reporting big issues to its board — not for loop execution. Cost if wrong: `rafa loop start` is a second execution engine, and running both would double-dispatch every task; declining it loses rafa's per-session effort granularity, recoverable afterwards via `rafa effort collect`.

Marcos asked for this explicitly. Cost if wrong: a task's tests pass locally against stale `node_modules` and fail for the next implementer.

Shipping a named one-character hole in the project's only mechanical guarantee, with the implementer one message away, is the worse call. `SELECT ... INTO` stays a documented limit, since it is a different statement shape and chasing it is scope creep.
- the `E'...\'...'` behaviour change needs a deliberate decision rather than acceptance. A backslash-escaped quote now throws "unterminated string" where the old code mis-scanned silently — failing closed is right, but `E''` is legal Postgres, so a legitimate hand-written migration would fail the lint with an opaque message. Either honour the escape or make the message name `E''` and backslash escapes explicitly. A lint that rejects valid SQL with an unactionable message is how a contributor concludes the tool is broken and stops using it, which costs more than the rule is worth.
