# Service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the foundation's tables and pure functions into a service you can start: an API-key layer, an MCP surface over everything that exists, an internal HTTP layer for the web app, and a backup schedule.

**Architecture:** Three layers already exist — Zod schemas, pure domain functions, Drizzle tables. This plan adds the two missing ones between them: a repository layer that is the only code reaching the tables, and a surface layer that validates with a shared Zod object before calling a repository. One Zod object per operation serves the MCP tool and the HTTP route, so the two cannot drift. Both servers are thin entry files; everything they register lives in pure functions a test can call without starting a process.

**Tech Stack:** Bun, TypeScript, Postgres 16, Drizzle ORM, Zod 4, `@open-tomato/service*` (chassis), `@modelcontextprotocol/sdk`, Express 5, `bun:test`.

**Spec:** [docs/superpowers/specs/2026-11-03-job-application-tracker-design.md](../specs/2026-11-03-job-application-tracker-design.md) — build order steps 6, 7 and 8.

## Global Constraints

- Postgres 16 in the Docker container; Drizzle with **real migrations**. Never `drizzle-kit push`.
- Pinned chassis packages, exactly these ranges: `"@open-tomato/service": "^1.0.1"`, `"@open-tomato/service-mcp": "^1.0.1"`, `"@open-tomato/service-express": "^1.0.2"`, `"@open-tomato/service-logger": "^1.0.0"`. **Never depend on `@open-tomato/service-errors`** — it exists only as an unpublished 0.0.0 package on a local branch.
- Read package names and versions from npm or the standalone `github.com/open-tomato/service` repo, never from the `open-tomato/packages/service/` monorepo copy, which names the same packages `service-core`, `mcp`, `express` at 0.1.1 and never published them.
- Zod schemas are the single source for MCP tool definitions and HTTP routes. Validation runs before any call reaches the data layer.
- Every collection operation has a **bulk and a single** form.
- Bun runtime, `bun:test`. 80% coverage minimum, TDD.
- Source files under 800 lines, functions under 50 lines, immutable updates, nesting no deeper than 4.
- **No vocabulary in code.** Code never branches on a registry row's `key` or `label`. It branches on the user-set booleans `is_shortlist`, `is_applied`, `is_terminal`, `is_repeatable`, `is_traction`, and on the internal discriminators `kind` and `confidence`.
- `bun run lint:migrations` stays exit 0, and `bunx drizzle-kit check` stays clean.
- No `console.log`. Use the chassis logger from `ServiceContext.logger` / `MCPContext.logger`.
- No device name, host name, IP address or self-hosted-runner detail in any committed file (§12.3).
- Errors never leak a connection string, a key, or a SQL fragment to a caller.

## Out of Scope

Named here because the spec lists them next to in-scope work and an implementer would otherwise invent them:

- **MCP tool group 10, claims and series** (§11.1 item 10). The `claim`, evidence and series tables from §7.9 do not exist. They belong to the market-stats plan with their own migration.
- **The pipeline-level reads** (§8.1): how many positions each requirement limits, the what-if that marks a requirement closed and reports which positions flip, and bottlenecks ranked by unlock-per-cost over `detour.cost_amount`. The spec places them under scoring but no build-order step claims them, and they are aggregate reads over the same rows the own-funnel half of Stats counts. They go with the market-stats plan, which owns the Stats surface. This plan stores every column they need and adds no tool for them.
- **The web app** (§13). This plan serves it and stops there.
- **Capture drivers and the enrichment pass** (§11.3). The shipped default is agent paste, which is the MCP tools this plan builds.
- **The seed interview** (§11.4). It is a documented prompt over the registry tools, written once the tools exist.

## Review Focus

Five input classes the spec implies, each wired to the task that owns the code:

1. **An empty or unset `API_KEY`** must make the middleware refuse every request, never allow all of them. Fail-open is the default failure mode of hand-rolled key checks. → Task 9.
2. **A write naming an archived registry row** must be refused, while a read of a row that was archived after it was referenced must still return its label. Archival is not deletion. → Task 3.
3. **A bulk call where one item fails** must leave nothing behind and must name the failing item's index. → Task 4.
4. **`app_config.criteria_mode` holding an unrecognised string**, hand-edited into the jsonb, must fall back to `versioned` and log, not crash the board. → Task 5.
5. **A position whose latest stage event has a null `stage_id`** (the registry ships empty) must not be read as "applied", so the re-score move rule may move it. → Task 7.

## Task 3: Registry repositories, and the archival rule

**Files:**
- Create: `src/data/repositories/db.ts`
- Create: `src/data/repositories/registries.ts`
- Create: `src/schemas/common.ts`, `src/schemas/registries.ts`

**Interfaces:**
- Consumes: every registry table from `src/data/schema/registries.ts`; `ArchivedError`, `NotFoundError`.
- Produces:
  - `export type Db` — `DrizzleClient` or a transaction client, so every repository function takes either.
  - `export const REGISTRY_TABLES` — a record from registry name to its table object, covering all twelve of §7.1. The name is the surface's parameter; the table is never chosen by string concatenation.
  - `export type RegistryName = keyof typeof REGISTRY_TABLES`
  - `listRegistry(db: Db, name: RegistryName, opts?: { includeArchived?: boolean }): Promise<RegistryRow[]>`
  - `addRegistryRows(db: Db, name: RegistryName, rows: readonly RegistryRowInput[]): Promise<RegistryRow[]>`
  - `archiveRegistryRow(db: Db, name: RegistryName, id: number): Promise<RegistryRow>`
  - `assertNotArchived(db: Db, name: RegistryName, id: number): Promise<void>` — the guard every other repository calls before storing a registry reference.
  - From `src/schemas/common.ts`: `IdSchema`, `PaginationSchema`, and `bulkOf<T>(item: T)` returning `z.object({ items: z.array(item).min(1).max(BULK_MAX) })` with `export const BULK_MAX = 500`.

A cap on bulk exists because an unbounded array is a memory and lock-duration risk on a single-user local database, and 500 is far above any plausible paste. Four registries carry a `key` and a `sort`, and `phase`/`stage` carry the user-set booleans, so `RegistryRowInput` is a discriminated set rather than one shape — `src/schemas/registries.ts` holds one schema per registry name and `REGISTRY_SCHEMAS` maps name to schema.

## Task 7: Stages, dispositions, and the re-score move rule

**Files:**
- Create: `src/data/repositories/dispositions.ts`
- Create: `src/schemas/dispositions.ts`
- Test: `tests/repositories/dispositions.test.ts`

**Interfaces:**
- Consumes: `positionStageEvent`, `positionDisposition`, `phase`, `stage`, `Db`, `assertNotArchived`.
- Produces:
  - `appendStageEvent(db: Db, input: { positionId: number; stageId: number | null; occurredAt?: Date; note?: string }): Promise<StageEvent>` — the **only** writer of the table. The module exports no update and no delete, which is how §7.6's append-only rule is enforced: the migration lint forbids routines, so there is no trigger to do it.
  - `currentStage(db: Db, positionId: number): Promise<StageRow | null>` — the latest event by `(occurredAt, id)`, with its stage's flags; null when there is no event, or when the latest event's `stageId` is null.
  - `setAside(db: Db, input: { positionId: number; setAsideReasonId: number; note?: string }): Promise<Disposition>`
  - `recordRejection(db: Db, input: { positionId: number; rejectionReasonId: number; note?: string }): Promise<Disposition>`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces:
  - `generateApiKey(): string` — 32 bytes from `crypto.getRandomValues`, base64url, prefixed `jat_`.
  - `verifyApiKey(presented: string, expected: string): boolean` — compares SHA-256 digests with `crypto.timingSafeEqual`, so the comparison takes the same time whatever the input, and length never leaks through an early return.
  - `requireApiKey(expected: string | undefined): RequestHandler` — reads `Authorization: Bearer <key>`, calls `verifyApiKey`, and responds 401 with `{ error: 'unauthorized' }` otherwise. **When `expected` is undefined or empty, every request is refused with 503 and the reason logged.** The body never echoes the presented value.

**Do not use the chassis's `auth` config or `ctx.requireAuth` for this.** `ServiceConfig.auth` accepts only `{ introspectUrl, introspectSecret }` and `buildRequireAuth` calls `POST /introspect` on a separate auth service, which this template does not have. Leaving `auth` unset makes `ctx.requireAuth` a **passthrough that allows everything**, so mounting it would read as protection and provide none. §12.1 wants one env-var key, so the middleware is ours and `ctx.requireAuth` is never mounted.

What `startService` does:

1. Wraps the Postgres pool in `createDependency({ name: 'postgres', client: db, onStart, onStop })`, so the chassis starts and stops it in order.
2. Calls `createService({ serviceId: 'job-application-tracker', port, dependencies: [pool], register })`.
3. In `register`: mounts `requireApiKey(process.env.API_KEY)` on `/api` **only when `API_KEY` is set**, logs loudly when it is not, then `mountRoutes(app, db)`.
4. Serves the web bundle with `express.static(WEB_DIST)` when that directory exists, so one process serves the app and the API from one origin.

Leave `cors` unset: §11.2 has one origin and one port, so a CORS block in the template would be configuration nobody needs. Leave `auth` unset as well, and never mount `ctx.requireAuth` (Task 9 says why).

Loopback without a key is Marcos's explicit choice, so step 3's conditional is deliberate: on a machine with no `API_KEY` the local client still works, and the log line is what makes the exposure deliberate rather than accidental.

## Task 17: Backups

**Files:**
- Create: `src/backup/retention.ts`, `src/backup/dump.ts`, `src/backup/schedule.ts`

**Interfaces:**
- Consumes: `readBackupSettings` from Task 5, `createDependency`.
- Produces:
  - `planRetention(files: readonly BackupFile[], keep: number): { keep: BackupFile[]; drop: BackupFile[] }` — pure, newest first by name, which is why names carry a sortable UTC timestamp.
  - `runDump(opts: { databaseUrl: string; outDir: string; now: Date; spawn: Spawner }): Promise<string>` — the path written. `Spawner` is injected, so no test runs `pg_dump`.
  - `startBackupSchedule(opts: { db: Db; outDir: string; spawn?: Spawner }): Promise<{ stop(): Promise<void> }>` — reads interval and `keep` from `app_config`, and returns immediately without a timer when backups are off.

§12.2 wants retention that **replaces rather than accumulates**: default `keep: 1` and a fortnightly interval, both in `app_config` under `backup`, and `{ enabled: false }` turns the whole thing off with one setting. The dump directory goes in `.gitignore`: a dump is the personal data the whole design exists to keep out of the repository.

The `pg_dump` binary path comes from `PG_DUMP_BIN`, default `pg_dump`. A spawned child needs care — read the `bun-spawn-child-readings` skill before writing `runDump`, because a killed child's exit code and a quit pipe both read misleadingly.
